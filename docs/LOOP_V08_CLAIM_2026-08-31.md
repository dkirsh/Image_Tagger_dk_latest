# Loop v0.8 — claim document

*Written 2026-08-31, before any v0.8 code exists. Method-card order: the claims and their
refutations are recorded first so the implementation can be tested against them rather than
described by them afterwards.*

**Base:** `6f904ae3ce11d041fcd86dc19c8c63c05669c943`. `loop/orchestrate.py` and
`loop/run_loop_compare.py` are byte-identical to their blobs at `5fb46e39`, the commit both
round-7B passes reviewed, so the defects below are being fixed in the code that was actually
attacked.

**Why v0.8 exists.** Two independent 7B passes — Codex's blind review of record, and a
same-lineage pre-check from this lane — converged on the same two defects and on the same
four repairs holding. The reports differ on one point of fact: the orchestrator suite is
15/15 here and 14/15 under Codex, with `test_timeout_terminates_producer_descendants`
failing there. The working hypothesis, still under test in the Codex lane and **not assumed
by this document**, is that the Codex CLI sandbox denies `killpg` against new-session
processes, which makes the `EPERM` path deterministic there and rare here. Every claim below
is written to hold under *both* outcomes, because a fix that only works where the bug does
not reproduce is not a fix.

---

## C1 — Teardown (this lane's 7B-5; Codex's 7B-1)

**The defect.** `_kill_process_group` and `_signal_pids` catch only `ProcessLookupError`. A
`PermissionError` from `killpg` therefore escapes, aborts the kill escalation part-way,
displaces the `TimeoutExpired` being handled, and surfaces through `run_cycle`'s
`except OSError` as `REFUSED: producer could not start` — for a producer that started, ran,
and blew its deadline.

**Claims.**

1. A failure to signal any single target never aborts the sweep. Every remaining target is
   still attempted.
2. A signalling failure never displaces `TimeoutExpired`, and never changes the diagnosis. A
   producer that timed out is reported as having timed out.
3. The final `SIGKILL` sweep always runs.
4. `_kill_process_group` and `_signal_pids` distinguish two outcomes and treat neither as
   fatal: `ProcessLookupError` means *gone*, and `PermissionError` or any other `OSError`
   means *could not signal*. Both are recorded; neither is raised.
5. Descendant enumeration polls at short intervals **during** the run and accumulates the PID
   set, so a short-lived intermediate is seen before it exits and orphans its children. A
   single snapshot taken after the deadline cannot see a process that has already gone.
6. Any PID the sweep could not confirm dead is named in the refusal message, and — when a
   summary is written — in a `teardown_incomplete` field.

**Residual limitation, stated in the contract rather than papered over.** A producer that
double-forks into a new session *before the first poll* can leave the ancestry graph
entirely, and no amount of `ps`-walking will find it afterwards. What v0.8 guarantees is a
**bounded return time and complete reporting**, not a kill guarantee against an adversarial
producer. Anyone reading `teardown_incomplete` should read it as "these PIDs were still
alive when we gave up", not as "the orchestrator failed".

**Refutation.** Monkeypatch `os.killpg` to raise `PermissionError` unconditionally: the
refusal message must still say *timed out*, and the final `SIGKILL` sweep must still execute.
Separately, Codex's orphaned-grandchild attack must end in one of exactly two states — a
reaped grandchild, or an explicit `teardown_incomplete` report. A silent success, where the
orchestrator reports a clean timeout while a descendant is still running unreported, refutes
this claim.

## C2 — Summary write (this lane's 7B-3)

**The defect.** `orchestrate.py:242` writes the run summary through an unguarded
`open("x")`. Every sibling write in the module is guarded; this one is not. A
`run_summary.json` appearing in the run directory mid-run produces an uncaught
`FileExistsError`, exit 1, and a traceback, where the contract promises exit 2.

**Claim.** That write is guarded. `FileExistsError` and any other `OSError` map to the
refusal tuple with exit 2 and a message naming the foreign `run_summary.json`. No traceback
reaches the operator.

**Refutation.** A producer that drops a `run_summary.json` into the run directory mid-run
must yield exit 2. Exit 1, or a traceback on stderr, refutes.

---

## C3 — Determinism

**Claim.** `test_timeout_terminates_producer_descendants` passes deterministically under both
`EPERM` and non-`EPERM` signalling — that is, on this machine and in a sandbox that denies
`killpg`.

**Refutation.** Run it 20× with `os.killpg` patched to raise `PermissionError`, and 20×
unpatched. Any failure in either set refutes. This is the claim that decides whether the
15/15 ÷ 14/15 disagreement is closed or merely hidden on one of the two machines.

## Scope, and one thing deliberately not done

Touched: `loop/orchestrate.py` and `loop/tests/test_orchestrate.py`, plus this document.

Untouched, by instruction: `loop_runs/`, `annotation_socket`, the M1 audit, corpus CSVs,
Hough, MPIB.

**`CONTRACT_VERSION` is deliberately left at `render-verdict/v0.7`,** and this needs saying
plainly because the brief asked for a v0.8 bump. That constant is not a documentation
version. It is the producer↔comparator wire string: `run_loop_compare.py:266` compares it
against the packet manifest and refuses on mismatch. Bumping it would refuse every existing
v0.7 packet — the committed milestone runs, the committed wrong-wall stub, and Stephan's
producer at `New_VR_Platform@fb3a873` — for a change that alters nothing a producer emits or
consumes. Everything in v0.8 is orchestrator-internal process handling.

So "v0.8" here names the orchestrator's documented behaviour, carried in this document and in
the module's METHOD BLOCK, while the wire contract stays where it is. If the intent was to
re-version the wire, that is a coordinated break needing Stephan and a producer bump, and it
should be its own decision rather than a side effect of a teardown fix.

## Amendment, 2026-08-31, after the Codex probe — C1b

*Appended after the probe reported back. The original claims above are left exactly as
written; this is an addition, not a revision.*

**What the probe found.** Inside the Codex CLI sandbox, `os.killpg` against a new-session
child **succeeded** ("killpg ok"), while executing `ps` raised
`PermissionError: [Errno 1] Operation not permitted: 'ps'`. That inverts the hypothesis this
document was written under: the sandbox denies process *enumeration*, not process *signalling*.

**One correction to the mechanism, checked against the code rather than inferred.** The brief
attributed the deterministic 14/15 to `_descendant_pids` raising `OSError` out of the timeout
handler. It does not. At `5fb46e39` — and in the v0.8 working tree before this amendment —
`_descendant_pids` already caught `(OSError, subprocess.TimeoutExpired)` and returned an empty
set. Executed against the pre-amendment tree with `ps` denied:

```
_descendant_pids(1)                    -> set()      (returns; does not raise)
timed-out producer, ps denied          -> exit 2, "producer timed out at iter 0 after 0.05s"
clean producer run, ps denied          -> exit 0, STOPPED_BELOW_THRESHOLD
```

So a denied `ps` did not displace the diagnosis on this machine, and the `PermissionError`
traced in 7B-5 came from `os.killpg` at line 76, with a stack recorded at the time. Whatever
produced Codex's 14/15, this particular call path was already guarded against raising.

**But the requirement stands, and names a real defect.** Returning an empty set on a failed
enumeration is silent in a way that lies. `teardown_incomplete: []` — or the field's absence —
reads as *we looked and found nothing*, when the truth is *we could not look*. A reader
auditing a run has no way to tell those apart. That is worth fixing whether or not it was the
cause of the 14/15.

**C1b claims.**

1. `_descendant_pids` never raises. It catches `OSError`, a `ps` timeout, a non-zero `ps`
   exit, and anything else, returning the pids found so far together with an error string.
2. When enumeration failed at any point in a run, the refusal message carries
   `descendant enumeration unavailable: <errno text>`.
3. When enumeration failed and a summary is written, the summary carries
   `descendant_enumeration_failed: true` and the error text.
4. Every call inside the `except TimeoutExpired` handler and the `finally` block follows the
   same never-raise discipline, so no second failure can displace the first diagnosis or skip
   the `SIGKILL` stage.

**C1b refutation.** Patch the `ps` invocation — and only that — to raise
`PermissionError(1, "Operation not permitted", "ps")`. Then: (a) a timed-out producer is still
reported as timed out, the `SIGKILL` stage is still attempted, and the message carries the
enumeration-unavailable note; (b) a clean producer run under the same patch still returns 0
with `descendant_enumeration_failed` in the summary, never "could not start".

**Residual limitation, strengthened by the probe.** Codex's escalated probe confirms that an
orphaned new-session grandchild is invisible to `ps` ancestry on macOS regardless of sandbox —
once the intermediate exits, the child reparents and the ancestry walk cannot reach it. Polling
during the run narrows the window but does not close it. The guarantee remains bounded return
plus honest reporting, and v0.8 now reports the difference between *nothing survived* and
*we could not tell*.

**`orchestrator_version`.** `run_summary` had no field naming which orchestrator wrote it, so
`"orchestrator_version": "0.8"` is added. `CONTRACT_VERSION` stays `render-verdict/v0.7`, as
agreed — the wire is unchanged.

## Amendment, 2026-09-01, after Codex round 7c — C3c

*Appended after the 7c review of `4a93b06c`. The original C3 above is left exactly as
written; this narrows what the suite may assert, and does not touch the code's behaviour.*

**What 7c found, and what it did not.** Codex returned NO GO on two findings, and both are
**test expectations rather than code behaviour**. It verified, against the pinned tree in a
sandbox where `ps` is denied, that every behavioural claim in this document holds: the
timeout diagnosis stays honest (`timed out`, never `could not start`), the `SIGKILL` stage is
reached with `killpg_attempt_signals: [15, 9]`, clean runs exit 0 carrying
`descendant_enumeration_failed` and the error text, all three foreign-summary squats — file,
directory and symlink — refuse with exit 2 and no traceback, and the comparator is 44/44.
Nothing in C1, C1b or C2 was refuted.

What failed is the suite's own expectations:

- `test_timeout_terminates_producer_descendants` asserts `not marker.exists()`
  unconditionally, which is **unsatisfiable** where enumeration is unavailable — it demands a
  kill guarantee for precisely the case C1's residual limitation says cannot be guaranteed.
  0/20 in that sandbox.
- `test_orphaned_new_session_grandchild_is_reaped_or_reported` offers the disjunction
  *reaped or reported*, but its "reported" arm only looks for `teardown_incomplete` and so
  misses the honest report that is actually emitted: `descendant enumeration unavailable`.

So the suite was demanding of the code something this very document had already declined to
promise. That is a defect in the test, and leaving a deterministically red test while
claiming the 15/15 ÷ 14/15 disagreement is closed would be worse than the red test itself.

**C3c — the principle the suite must follow.** The suite asserts **exactly the contract
disjunction and nothing stronger**: bounded return, plus *reaped or reported*. It must be
green both where `ps` works and where `ps` is denied, and it must be green for the right
reason in each case rather than by being weakened until it cannot fail.

Concretely, both descendant tests branch on what the refusal message actually reports:

- If the message carries `descendant enumeration unavailable`, the **honest-report arm**
  applies. Assert that the run is reported as timed out, that the `SIGKILL` stage was
  attempted, and that the message makes no false claim of a clean sweep. Do **not** require
  the marker to be absent — the contract does not promise a kill when we could not look.
- Otherwise the **strong arm** applies, unchanged and undiminished: the descendant is
  terminated, exactly as asserted today.

**Refutation.** Weakening the working-`ps` arm refutes C3c. If the strong arm ever stops
requiring the descendant to die where enumeration succeeds, the suite has been tuned to pass
rather than to test, and this amendment has been violated. Equally, a green suite in the
denied-`ps` sandbox that does not check the `SIGKILL` attempt and the honest report would be
green for no reason worth having.

**Scope, stated in advance.** v0.8.1 is **tests plus this amendment only**. If satisfying
either 7c finding turns out to require a change to `loop/orchestrate.py`, that is evidence
the findings are not merely test expectations after all, and the right response is to stop
and report rather than to edit the code under a tests-only mandate.

## Amendment, 2026-09-01 — C3d: the orphan test was asserting luck

*Appended after measuring the committed test. C3c above stands; this records why one of its
two arms could not be satisfied as written, and how the suite is repaired.*

**The measurement that settles it.** Running the **unmodified** orphan test from the
committed `4a93b06c` twenty times on this machine, with `ps` working normally:

```
COMMITTED 4a93b06c orphan test, ps WORKING: 2/20 passed
```

Two in twenty. So `test_orphaned_new_session_grandchild_is_reaped_or_reported` was
**flaky-green** when v0.8 landed — it passed the single run in the suite and would have
failed most of the time had anyone repeated it. It was asserting luck rather than the
contract, and the v0.8 commit inherited that without knowing.

**Why it cannot hold as written.** The test's producer sleeps 0.01s and exits, orphaning its
new-session grandchild inside ten milliseconds — against a 20 ms enumeration poll. By the
time the 0.05s deadline fires, the intermediate is gone and the grandchild has reparented, so
the ancestry walk finds nothing. Enumeration *succeeded*; there was simply nothing left to
see. The run therefore emits no `descendant_enumeration_failed` and no `teardown_incomplete`,
and the grandchild surfaces later to write its marker. Neither *reaped* nor *reported* holds.

That is exactly the scenario C1's residual limitation already documents as unobservable —
"a producer that double-forks into a new session before the first poll can leave the ancestry
graph entirely, and no amount of `ps`-walking will find it afterwards". The test was
demanding of the code the one thing this document had explicitly declined to promise.

**The repair: one test becomes two, each asserting what the contract promises for its own
scenario.**

1. **Strong arm, rescoped.** The orphan producer now keeps its intermediate alive comfortably
   past the first enumeration poll — 0.5s against a 20 ms interval — so the grandchild is
   genuinely observable. For that case *reaped or reported* must hold **strictly**, and the
   arm is not weakened in any other respect. Where `ps` is denied, the honest-report arm from
   C3c applies instead.
2. **Limitation test, new and named for its purpose.** The sub-10 ms escape is kept as its own
   test, asserting **only** the bounds the contract actually promises: exit 2, a message
   saying *timed out*, bounded return, no traceback, and no false claim of a clean sweep. It
   must **not** assert that the grandchild dies or is reported, because the contract does not
   promise that. Its docstring points here.

Together the two cover both scenarios, and neither passes by luck. Splitting them is not a
weakening: the strong assertion survives intact for the case where it is meaningful, and the
case where it is meaningless gets assertions that are true by contract rather than by timing.

**Open work, deliberately deferred rather than done.** There is a third possibility, and it is
a code change, so it is out of scope under a tests-only mandate: `orchestrate.py` could notice
that a producer exited while a spawn was in flight and report *a descendant may have escaped
observation*, which would turn the fast-escape case from silent into reported. That would let
the strong arm apply to both scenarios. It is recorded here as open work for a future version,
not implemented in v0.8.1. `loop/orchestrate.py` is untouched by this amendment.
